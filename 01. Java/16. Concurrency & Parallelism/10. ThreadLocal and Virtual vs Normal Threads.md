## Introduction

**🔧 Technical Overview - ThreadLocal and Virtual Threads Architecture**:
- **ThreadLocal Implementation**: Uses a ThreadLocalMap stored in each Thread object, providing O(1) access to thread-specific variables without synchronization overhead
- **Virtual Thread Architecture**: Lightweight threads managed by the JVM runtime, using continuation-based implementation to achieve massive concurrency
- **Memory Model Integration**: ThreadLocal variables maintain proper happens-before relationships and visibility guarantees within thread boundaries
- **Carrier Thread Mapping**: Virtual threads are mounted/unmounted on platform threads (carrier threads) dynamically, enabling efficient resource utilization
- **Stack Management**: Virtual threads use heap-allocated stacks that can be resized and moved, unlike platform threads with fixed-size native stacks
- **Scheduling Optimization**: ForkJoinPool-based scheduler manages virtual thread execution with work-stealing algorithms for optimal load distribution
- **I/O Integration**: Virtual threads integrate with NIO and blocking I/O operations, automatically yielding when blocked to maximize throughput

ThreadLocal provides thread-confined variables, while Virtual Threads (introduced in Java 19 as preview, stable in Java 21) revolutionize concurrent programming by enabling lightweight, high-throughput applications with millions of threads.

**🔧 Technical Deep Dive - Internal Implementation and Performance Characteristics**:
- **ThreadLocalMap Structure**: Each Thread contains a ThreadLocalMap that uses weak references to ThreadLocal objects as keys, preventing memory leaks when ThreadLocal instances are garbage collected
- **Hash Collision Handling**: Uses linear probing with expunge operations to handle hash collisions and clean up stale entries automatically
- **Virtual Thread Continuation**: Based on Project Loom's continuation API, allowing thread execution to be suspended and resumed efficiently
- **Pinning Behavior**: Virtual threads are "pinned" to carrier threads during synchronized blocks and native calls, potentially reducing concurrency benefits
- **Memory Overhead**: Virtual threads require ~200 bytes vs ~2MB for platform threads, enabling millions of concurrent threads
- **Context Switching**: Virtual thread context switches are managed by JVM (user-space) rather than OS kernel, providing microsecond-level switching times
- **Structured Concurrency**: Designed to work with structured concurrency patterns, providing better error handling and resource management
- **Debugging Integration**: Enhanced debugging support with virtual thread-aware profiling tools and stack trace management

## ThreadLocal Fundamentals

**🔧 Technical Overview - ThreadLocal Implementation and Memory Management**:
- **ThreadLocalMap Architecture**: Each Thread object contains a ThreadLocalMap field that stores thread-specific values using ThreadLocal instances as keys
- **Weak Reference Keys**: ThreadLocalMap uses WeakReference<ThreadLocal<?>> as keys, allowing ThreadLocal objects to be garbage collected even when values remain
- **Hash Table Implementation**: Uses open addressing with linear probing for collision resolution, optimized for the common case of few ThreadLocal variables per thread
- **Entry Cleanup**: Automatically removes stale entries during get(), set(), and remove() operations to prevent memory accumulation
- **Inheritance Support**: InheritableThreadLocal allows child threads to inherit values from parent threads at creation time
- **Performance Characteristics**: O(1) average-case access time with minimal synchronization overhead since each thread accesses only its own map
- **Memory Layout**: ThreadLocal values are stored in the thread's own memory space, eliminating cache coherency issues between threads

### Basic ThreadLocal Usage

**🔧 Technical Deep Dive - ThreadLocal Access Patterns and Optimization Strategies**:
- **Access Pattern Optimization**: ThreadLocalMap is optimized for the common pattern of few ThreadLocal variables accessed frequently by the same thread
- **Hash Code Generation**: Uses a special hash code increment (0x61c88647) that provides good distribution in power-of-two sized hash tables
- **Lazy Initialization**: ThreadLocalMap is created only when the first ThreadLocal variable is set, reducing memory overhead for threads that don't use ThreadLocal
- **Expunge Operations**: Proactive cleanup of stale entries during normal operations to maintain performance and prevent memory bloat
- **Rehashing Strategy**: Automatic table resizing when load factor exceeds threshold, with special handling for stale entries during rehash
- **Thread Safety**: No external synchronization required since each thread accesses only its own ThreadLocalMap instance
- **JIT Optimization**: HotSpot JVM can optimize ThreadLocal access patterns through escape analysis and stack allocation
- **Memory Barriers**: Proper memory barrier placement ensures visibility of ThreadLocal values within the owning thread

public class ThreadLocalBasics {
    
    // Simple ThreadLocal
    private static final ThreadLocal<Integer> threadLocalValue = new ThreadLocal<Integer>() {
        @Override
        protected Integer initialValue() {
            return 0;
        }
    };
    
    // ThreadLocal with Supplier (Java 8+)
    private static final ThreadLocal<String> threadLocalString = 
        ThreadLocal.withInitial(() -> "Thread-" + Thread.currentThread().getId());
    
    public static void basicExample() {
        System.out.println("=== Basic ThreadLocal Example ===");
        
        Runnable task = () -> {
            String threadName = Thread.currentThread().getName();
            
            // Each thread has its own copy
            System.out.println(threadName + " initial value: " + threadLocalValue.get());
            System.out.println(threadName + " initial string: " + threadLocalString.get());
            
            // Modify thread-local values
            threadLocalValue.set(threadLocalValue.get() + 10);
            threadLocalString.set(threadLocalString.get() + "-modified");
            
            System.out.println(threadName + " modified value: " + threadLocalValue.get());
            System.out.println(threadName + " modified string: " + threadLocalString.get());
        };
        
        Thread thread1 = new Thread(task, "Thread-1");
        Thread thread2 = new Thread(task, "Thread-2");
        Thread thread3 = new Thread(task, "Thread-3");
        
        thread1.start();
        thread2.start();
        thread3.start();
        
        try {
            thread1.join();
            thread2.join();
            thread3.join();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
    
    public static void main(String[] args) {
        basicExample();
    }
}

### ThreadLocal Memory Leaks and Cleanup

**🔧 Technical Overview - Memory Leak Prevention and Resource Management**:
- **Weak Reference Mechanism**: ThreadLocalMap uses WeakReference keys to prevent ThreadLocal instances from being retained when no longer referenced
- **Stale Entry Detection**: Entries become "stale" when their ThreadLocal key is garbage collected, but the value reference remains in the map
- **Automatic Cleanup Triggers**: Cleanup occurs during get(), set(), remove(), and rehash operations when stale entries are encountered
- **Thread Pool Memory Leaks**: Long-lived threads in thread pools can accumulate ThreadLocal values indefinitely without explicit cleanup
- **ClassLoader Leaks**: ThreadLocal values can prevent class unloading in application servers, leading to PermGen/Metaspace memory leaks
- **Reference Chain Analysis**: Understanding the reference chain: Thread → ThreadLocalMap → Entry[] → WeakReference<ThreadLocal> + Value
- **Cleanup Best Practices**: Always call remove() in finally blocks, especially in thread pool environments and web applications

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class ThreadLocalMemoryManagement {
    
    // Problematic ThreadLocal - can cause memory leaks
    private static final ThreadLocal<ExpensiveObject> problematicThreadLocal = new ThreadLocal<>();
    
    // Better ThreadLocal with cleanup
    private static final ThreadLocal<ExpensiveObject> managedThreadLocal = new ThreadLocal<ExpensiveObject>() {
        @Override
        protected ExpensiveObject initialValue() {
            return new ExpensiveObject("Managed-" + Thread.currentThread().getId());
        }
    };

        private final String name;
        private final byte[] data = new byte[1024 * 1024]; // 1MB

            this.name = name;
            System.out.println("Created expensive object: " + name);
        }
        
        @Override
        protected void finalize() throws Throwable {
            System.out.println("Finalized expensive object: " + name);
            super.finalize();
        }
        
        public String getName() { return name; }
    }
    
    public static void demonstrateMemoryLeak() {
        System.out.println("=== Memory Leak Demonstration ===");
        
        ExecutorService executor = Executors.newFixedThreadPool(5);
        
        // Submit tasks that create ThreadLocal objects
        for (int i = 0; i < 10; i++) {
            final int taskId = i;
            executor.submit(() -> {
                // Create expensive object in ThreadLocal
                problematicThreadLocal.set(new ExpensiveObject("Problematic-" + taskId));
                
                // Use the object
                ExpensiveObject obj = problematicThreadLocal.get();
                System.out.println("Using object: " + obj.getName());
                
                // Simulate work
                try {
                    Thread.sleep(1000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                
                // NOTE: Not calling remove() - this can cause memory leaks!
                // problematicThreadLocal.remove(); // Uncomment to fix leak

## ThreadLocal Patterns

**🔧 Technical Overview - ThreadLocal Design Patterns and Use Cases**:
- **Request Context Pattern**: Stores request-scoped information (user ID, request ID, security context) that needs to be accessible throughout the request processing chain
- **Transaction Context Pattern**: Manages database connections, transaction state, and rollback information across service layer boundaries
- **Security Context Pattern**: Maintains authentication and authorization information for the current thread without passing security objects through method parameters
- **Logging Context Pattern**: Stores contextual information (correlation IDs, user information) for structured logging across all components in a request
- **Performance Monitoring Pattern**: Tracks timing information, performance metrics, and profiling data for the current operation
- **Resource Management Pattern**: Manages thread-local resources like formatters, parsers, and expensive-to-create objects that are not thread-safe
- **State Machine Pattern**: Maintains thread-local state for complex workflows or multi-step processes that span multiple method calls

### Request Context Pattern

**🔧 Technical Deep Dive - Request Context Implementation and Performance Considerations**:
- **Context Propagation**: Request context must be manually propagated to child threads since ThreadLocal values are not automatically inherited
- **Memory Efficiency**: Context objects should be lightweight and avoid holding references to large objects to prevent memory issues
- **Cleanup Strategies**: Implement proper cleanup in web filters, servlet filters, or framework interceptors to ensure context is cleared after request completion
- **Thread Pool Integration**: Special consideration needed for thread pools where threads are reused across multiple requests
- **Nested Context Support**: Support for nested contexts in complex scenarios like async processing or sub-requests
- **Context Inheritance**: Use InheritableThreadLocal when child threads need access to parent context, but be aware of memory implications
- **Performance Optimization**: Context access should be optimized for frequent reads with minimal overhead
- **Error Handling**: Ensure context cleanup occurs even in exceptional circumstances to prevent context bleeding between requests

import java.util.UUID;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class RequestContextPattern {
    
    // Request context stored in ThreadLocal
    static class RequestContext {
        private final String requestId;
        private final String userId;
        private final long startTime;
        
        public RequestContext(String requestId, String userId) {
            this.requestId = requestId;
            this.userId = userId;
            this.startTime = System.currentTimeMillis();
        }
        
        // Getters
        public String getRequestId() { return requestId; }
        public String getUserId() { return userId; }
        public long getStartTime() { return startTime; }
        public long getElapsedTime() { return System.currentTimeMillis() - startTime; }
        
        @Override
        public String toString() {
            return String.format("RequestContext{requestId='%s', userId='%s', elapsed=%dms}", 
                               requestId, userId, getElapsedTime());
        }
    }
    
    // ThreadLocal to store request context
    private static final ThreadLocal<RequestContext> REQUEST_CONTEXT = new ThreadLocal<>();
    
    // Utility methods for context management
    public static void setRequestContext(String requestId, String userId) {
        REQUEST_CONTEXT.set(new RequestContext(requestId, userId));
    }
    
    public static RequestContext getRequestContext() {
        return REQUEST_CONTEXT.get();
    }
    
    public static void clearRequestContext() {
        REQUEST_CONTEXT.remove();
    }
    
    // Service layers that use the context
    static class AuthenticationService {
        public boolean authenticate(String token) {
            RequestContext context = getRequestContext();
            System.out.println("Authenticating request: " + context.getRequestId());
            
            // Simulate authentication
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            
            return token.startsWith("valid_");
        }
    }
    
    static class BusinessService {
        public String processRequest(String data) {
            RequestContext context = getRequestContext();
            System.out.println("Processing business logic for user: " + context.getUserId() + 
                             " (request: " + context.getRequestId() + ")");
            
            // Simulate business processing
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            
            return "Processed: " + data;
        }
    }
    
    static class AuditService {
        public void logRequest() {
            RequestContext context = getRequestContext();
            System.out.println("AUDIT: " + context + " - Request completed");
        }
    }
    
    // Request processor that ties it all together
    static class RequestProcessor {
        private final AuthenticationService authService = new AuthenticationService();
        private final BusinessService businessService = new BusinessService();
        private final AuditService auditService = new AuditService();
        
        public void processRequest(String requestId, String userId, String token, String data) {
            try {
                // Set up request context
                setRequestContext(requestId, userId);
                
                // Process request through various services
                if (authService.authenticate(token)) {
                    String result = businessService.processRequest(data);
                    System.out.println("Request result: " + result);
                } else {
                    System.out.println("Authentication failed for request: " + requestId);
                }
                
                // Log the request
                auditService.logRequest();
                
            } finally {
                // Always clean up context
                clearRequestContext();
            }
        }
    }
    
    public static void main(String[] args) {
        RequestProcessor processor = new RequestProcessor();
        ExecutorService executor = Executors.newFixedThreadPool(3);
        
        // Simulate multiple concurrent requests
        for (int i = 1; i <= 5; i++) {
            final int requestNum = i;
            executor.submit(() -> {
                String requestId = "REQ-" + UUID.randomUUID().toString().substring(0, 8);
                String userId = "USER-" + requestNum;
                String token = (requestNum % 2 == 0) ? "valid_token_" + requestNum : "invalid_token_" + requestNum;
                String data = "data_" + requestNum;
                
                processor.processRequest(requestId, userId, token, data);
            });
        }
        
        executor.shutdown();
        try {
            executor.awaitTermination(10, TimeUnit.SECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

## Virtual Threads (Project Loom)

**🔧 Technical Overview - Virtual Thread Architecture and Implementation**:
- **Continuation-Based Implementation**: Virtual threads use continuations (delimited call stacks) that can be suspended and resumed efficiently
- **Carrier Thread Mapping**: Virtual threads are multiplexed onto a pool of platform threads (carriers) using a M:N threading model
- **ForkJoinPool Scheduler**: Default scheduler uses ForkJoinPool with work-stealing for optimal load distribution across available CPU cores
- **Heap-Based Stacks**: Virtual thread stacks are allocated on the heap and can grow/shrink dynamically, unlike fixed-size platform thread stacks
- **Mounting and Unmounting**: Virtual threads are "mounted" on carrier threads during execution and "unmounted" when blocked or yielding
- **Pinning Detection**: Virtual threads become "pinned" to carrier threads during synchronized blocks or native calls, reducing parallelism
- **Memory Footprint**: Each virtual thread requires only ~200 bytes compared to ~2MB for platform threads, enabling millions of concurrent threads
- **I/O Integration**: Seamless integration with blocking I/O operations, automatically yielding when blocked to prevent carrier thread starvation

### Basic Virtual Thread Usage

**🔧 Technical Deep Dive - Virtual Thread Lifecycle and Performance Characteristics**:
- **Thread Creation Overhead**: Virtual thread creation is ~1000x faster than platform threads, with minimal JVM overhead
- **Context Switching**: User-space context switching managed by JVM scheduler, providing microsecond-level switching times
- **Stack Chunk Management**: Virtual thread stacks are composed of stack chunks that can be allocated and deallocated independently
- **GC Integration**: Virtual thread stacks are GC-managed heap objects, benefiting from modern garbage collection optimizations
- **Debugging Support**: Enhanced debugging with virtual thread-aware profilers and stack trace management tools
- **Thread Dump Analysis**: Special handling in thread dumps to manage potentially millions of virtual threads efficiently
- **Memory Pressure Handling**: Automatic stack chunk deallocation when virtual threads are blocked for extended periods
- **Platform Thread Pool Sizing**: Carrier thread pool size typically matches CPU core count for optimal CPU utilization

## Virtual vs Platform Threads

**🔧 Technical Overview - Platform vs Virtual Thread Architecture Comparison**:
- **Threading Model**: Platform threads use 1:1 mapping to OS threads, while virtual threads use M:N mapping with carrier threads
- **Memory Architecture**: Platform threads have fixed-size native stacks (1-2MB), virtual threads have dynamic heap-allocated stacks (~200 bytes initial)
- **Scheduling Mechanism**: Platform threads rely on OS scheduler with preemptive multitasking, virtual threads use cooperative JVM-managed scheduling
- **Context Switch Cost**: Platform threads require kernel-mode switches (~1-10 microseconds), virtual threads use user-space switches (~nanoseconds)
- **Creation Overhead**: Platform thread creation involves OS syscalls and stack allocation, virtual thread creation is pure JVM operation
- **Resource Limits**: Platform threads limited by OS thread limits (~thousands), virtual threads limited by heap memory (~millions)
- **I/O Handling**: Platform threads block carrier thread during I/O, virtual threads yield carrier thread for other virtual threads
- **CPU Utilization**: Platform threads can lead to thread pool exhaustion, virtual threads maintain optimal CPU utilization through work-stealing

### Performance Comparison

**🔧 Technical Deep Dive - Performance Analysis and Optimization Strategies**:
- **Throughput Characteristics**: Virtual threads excel in I/O-bound workloads with high concurrency, platform threads better for CPU-intensive tasks
- **Latency Considerations**: Virtual thread scheduling introduces minimal latency overhead, but pinning can cause performance degradation
- **Memory Utilization**: Virtual threads dramatically reduce memory footprint, allowing applications to handle millions of concurrent operations
- **GC Impact**: Virtual thread stacks are GC-managed, potentially increasing GC pressure but benefiting from modern GC optimizations
- **Cache Locality**: Platform threads maintain better cache locality, virtual threads may experience cache misses during carrier thread switches
- **Contention Handling**: Virtual threads reduce lock contention through better resource utilization, but synchronized blocks cause pinning
- **Monitoring Overhead**: Virtual thread monitoring requires specialized tools due to the large number of potential threads
- **Performance Profiling**: Traditional profiling tools may not accurately represent virtual thread performance characteristics

            String path = parts[1];
            
            // Skip headers
            String line;
            while ((line = in.readLine()) != null && !line.isEmpty()) {
                // Skip headers
            }

            try {
                Thread.sleep(100 + (int)(Math.random() * 200)); // 100-300ms
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }

            String response = generateResponse(method, path, requestId);
            
            // Send HTTP response
            out.println("HTTP/1.1 200 OK");
            out.println("Content-Type: text/html");
            out.println("Content-Length: " + response.length());

                clientSocket.close();

## Difficult Problems

**🔧 Technical Overview - Advanced Virtual Thread Challenges and Design Considerations**:
- **ThreadLocal Compatibility**: Virtual threads may not behave as expected with ThreadLocal variables due to carrier thread reuse
- **Pinning Issues**: Synchronized blocks and native calls pin virtual threads to carrier threads, reducing concurrency benefits
- **Memory Model Implications**: Virtual thread scheduling and carrier thread mapping can affect memory visibility and ordering guarantees
- **Debugging Complexity**: Traditional debugging and profiling tools may not work effectively with millions of virtual threads
- **Legacy Code Integration**: Existing code that assumes 1:1 thread mapping may not work correctly with virtual threads
- **Resource Management**: Different resource management strategies needed for virtual threads compared to platform threads
- **Performance Monitoring**: New metrics and monitoring approaches required to effectively observe virtual thread behavior
- **Error Handling**: Exception propagation and error handling patterns may need adjustment for virtual thread environments

### Problem: ThreadLocal with Virtual Thread Pool

**🔧 Technical Deep Dive - ThreadLocal and Virtual Thread Interaction Challenges**:
- **Carrier Thread Reuse**: Virtual threads may be unmounted and remounted on different carrier threads, potentially affecting ThreadLocal behavior
- **ThreadLocal Inheritance**: InheritableThreadLocal behavior with virtual threads may differ from platform threads due to different creation patterns
- **Memory Leak Prevention**: Traditional ThreadLocal cleanup strategies may not work effectively in virtual thread environments
- **Context Propagation**: Manual context propagation becomes more complex with virtual threads due to their lightweight nature
- **Scoped Values Alternative**: Java 20+ introduces Scoped Values as a virtual thread-friendly alternative to ThreadLocal
- **Performance Impact**: ThreadLocal access patterns may have different performance characteristics with virtual threads
- **Migration Strategies**: Approaches for migrating ThreadLocal-heavy code to work effectively with virtual threads
- **Testing Challenges**: Unit testing ThreadLocal behavior becomes more complex with virtual thread unpredictability

## Key Takeaways

1. **ThreadLocal Usage**: Ideal for request context, database connections, and thread-specific state, but requires careful cleanup to prevent memory leaks.
   - **Technical Insight**: ThreadLocal uses WeakReference keys in ThreadLocalMap to prevent memory leaks, but values can still cause leaks in thread pool environments. Always call remove() in finally blocks, especially in web applications and long-lived threads.

2. **Virtual Thread Benefits**: Enable massive concurrency (millions of threads), lower memory footprint, and simplified concurrent programming model.
   - **Technical Insight**: Virtual threads use continuation-based implementation with heap-allocated stacks (~200 bytes vs ~2MB for platform threads), managed by ForkJoinPool scheduler with work-stealing algorithms for optimal CPU utilization.

3. **Virtual Thread Limitations**: Not suitable for CPU-intensive tasks, ThreadLocal behavior may differ, and requires Java 19+ (preview) or Java 21+ (stable).
   - **Technical Insight**: Virtual threads become "pinned" to carrier threads during synchronized blocks and native calls, reducing concurrency benefits. CPU-intensive tasks don't benefit from virtual threads since they don't yield frequently.

4. **ThreadLocal vs Scoped Values**: Scoped values (Java 20+) are designed to work better with virtual threads and structured concurrency.
   - **Technical Insight**: Scoped values provide immutable, inheritable context that works better with virtual thread mounting/unmounting behavior and structured concurrency patterns, avoiding ThreadLocal's mutable state issues.

5. **Migration Strategy**: Gradually adopt virtual threads for I/O-bound workloads while keeping platform threads for CPU-intensive tasks.
   - **Technical Insight**: Identify I/O-bound services first, replace thread pools with virtual thread executors, address pinning issues by replacing synchronized with ReentrantLock, and monitor performance metrics during migration.

6. **Performance Considerations**: Virtual threads excel in I/O-heavy applications but may not improve CPU-bound performance.
   - **Technical Insight**: Virtual threads provide benefits when threads frequently block on I/O operations, allowing carrier threads to be reused. For CPU-bound tasks, the number of virtual threads should not exceed the number of CPU cores.

### 🔬 **Advanced Technical Concepts**

**ThreadLocal Implementation**:
- **Hash Table Design**: Uses open addressing with linear probing, optimized for few ThreadLocal variables per thread
- **Weak Reference Keys**: Prevents ThreadLocal instances from being retained, but values can still cause memory leaks
- **Automatic Cleanup**: Expunge operations during get(), set(), and remove() clean up stale entries proactively
- **Performance Optimization**: O(1) average access time with special hash code generation (0x61c88647) for good distribution

**Virtual Thread Architecture**:
- **Continuation API**: Based on delimited continuations that can suspend and resume execution efficiently
- **M:N Threading Model**: Multiple virtual threads multiplexed onto fewer platform threads (carriers)
- **Stack Management**: Heap-allocated stack chunks that can grow/shrink dynamically and be garbage collected
- **Scheduler Integration**: ForkJoinPool-based scheduler with work-stealing for optimal load distribution

**Memory Management**:
- **ThreadLocal Memory**: Each Thread object contains ThreadLocalMap with weak reference keys and strong reference values
- **Virtual Thread Memory**: Stack chunks allocated on heap, benefiting from modern GC optimizations
- **GC Integration**: Virtual thread stacks are GC-managed, potentially increasing GC pressure but improving memory utilization
- **Resource Cleanup**: Different cleanup strategies needed for ThreadLocal vs virtual thread environments

**Performance Characteristics**:
- **Context Switching**: Platform threads use kernel-mode switches, virtual threads use user-space JVM-managed switches
- **Creation Overhead**: Virtual thread creation ~1000x faster than platform threads
- **Memory Footprint**: Virtual threads enable millions of concurrent threads vs thousands for platform threads
- **I/O Handling**: Virtual threads automatically yield during blocking I/O, platform threads block the entire thread

**Concurrency Patterns**:
- **Request Context**: ThreadLocal for request-scoped data, Scoped Values for virtual thread environments
- **Resource Management**: Thread pools for platform threads, unlimited virtual threads with proper resource management
- **Error Handling**: Different exception propagation patterns needed for virtual thread environments
